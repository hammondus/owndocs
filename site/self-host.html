Self-host Own Docs

A Go backend, a Svelte front end, and one SQLite file. The build needs Go and Node; the deploy needs Docker.

Run it on your machine

To build the front end and the binary and start listening on 127.0.0.1:8484, run:

make run

Open http://127.0.0.1:8484, sign up, create a document, and open the same document in a second browser window to see it sync. To stop new accounts, start the server with -signup=closed and invite people with links instead.

Build and test

To run the Go vet, the Go tests, and the headless JavaScript suites:

make test

To drive the real interface in a real Chrome, which needs Chrome installed:

make test-ui

To build the front end and a binary for this machine without running it:

make build

Deploy

The deploy target is Linux on arm64, as a static binary with no runtime dependencies. To cross-compile it into dist/:

make release

On the server, with the repository checked out and Docker installed, to pull the latest commit and rebuild the container:

make deploy

The container runs as an unprivileged user and keeps its database in a data directory beside the compose file, so before the first start, create that directory and give it to user 65532. It closes signup. Put it behind the reverse proxy you already run; it speaks plain HTTP on port 8484.

Back it up

On the server, to write a verified, timestamped copy into ./data/backups:

make backup

The same against a local development database:

make backup-local

Both are safe while people are editing. Every backup is reopened and checked before it is reported as good. Do not back up by copying the database file: it runs in WAL mode, so a plain copy can be a valid database that is missing everything since the last checkpoint.

Scheduling is yours to own, and so is the second copy. The target above is on the same disk as the database, which helps with a mistake and not with a dead disk:

0 3 * * *  cd /srv/owndocs && make backup && rsync -a data/backups/ elsewhere:/owndocs/

To restore, stop the server, put the backup file at the database path, and start it again:

docker compose down
cp data/backups/docs-20260814T220345Z.db data/docs.db
docker compose up -d

Backups contain password hashes and live session tokens. They are written 0600; keep them that way wherever they are copied to.

Export to git

The exporter mirrors named versions into a git repository, one commit per version, authored by whoever named it and dated when they did. It is an ordinary client: it signs in with an account and sees only what that account can see. To run a single pass:

cd web
DOCS_EMAIL=you@example.com DOCS_PASSWORD=... \
  node scripts/exporter.mjs https://docs.example.com /path/to/repo --once

Without --once it polls. A document becomes a markdown file inside one directory per folder above it, and a sheet becomes a directory of one CSV per tab. Grant the account at each root folder it should mirror, and leave it there. The exporter never adds a remote; pushing somewhere is yours to arrange.

Notification email

Off unless you set -smtp, and the app is whole without it: mentions and replies always land in the in-app inbox. Mail covers the events where the recipient is by definition not in the app. It submits to a relay that already exists and never touches SPF, DKIM, DMARC, or bounces.

To turn it on, add the flags to docker-compose.yml, where command: is appended to the image's entrypoint:

command: ["-smtp", "relay.internal:587",
          "-mail-from", "owndocs@example.com",
          "-base-url", "https://docs.example.com"]
environment:
  SMTP_USERNAME: owndocs
  SMTP_PASSWORD: ...

-base-url is required with -smtp: the server has no other way to know its own public address, and a message whose only link is broken is worse than no message.

The same commands are in the repository's README, which the test suite checks against this page.
